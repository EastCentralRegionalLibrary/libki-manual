== Installation

=== One-step automatic install

Do you want to setup Libki as fast as possible and have a dedicated server? Then this is the choice for you. Just make sure your server is running Ubuntu 18.04, 20.04 or 22.04, or Debian 9 (Stretch), 10 (Buster) or 11 (Bullseye), and that you don't have a user named 'libki'. The installer refuses to run on other distributions, and stops immediately if the 'libki' user already exists. It must be run as root.

[source,bash]
----
wget -O- install.libki.org | bash
----

(By the way, that's the letter O, not the number 0.)

=== Alternative method

Not everyone wants to pipe a script directly from the web to bash.
It prevents you from reading the code you're about to run on your system.
If you want to read it through first, this alternative should be for you:

[source,bash]
----
git clone https://github.com/libki/libki-server.git
cd libki-server
bash install.sh
----

The installer also installs `libki-backup`, `libki-restore`, `libki-update`, `libki-translate` and `libki-setup` (the <<_setup_wizard,setup wizard>>) into `/usr/local/bin`.

If you answer "Yes" to the reverse proxy question, the Apache site is installed from `reverse_proxy.config`. It does not set a Libki instance: a normal server uses the default (empty) instance, and the administrator account created by the installer lives there.

=== Docker

The official Libki Server Docker image needs to be connected to a database server, it does not contain a MySQL instance within it.
Using a MySQL or a MariaDB container on the same Docker network is considered good practice.

The Libki Server image is available on https://hub.docker.com/r/libki/libki-server[Docker Hub].

The easiest way to get started is the <<_setup_wizard,setup wizard>>: `script/utilities/setup-wizard.sh --docker` writes `docker/.env` for you, with generated database passwords.

To do it by hand, create `docker/.env` next to `docker/docker-compose.yml`. Docker Compose reads these variables from that file:

----
LIBKI_ADMIN_USERNAME=<ADMIN_USERNAME> // <1>
LIBKI_ADMIN_PASSWORD=<ADMIN_PASSWORD>
LIBKI_INSTANCE= // <2>
LIBKI_TZ=America/Denver // <3>
LIBKI_PORT=3000 // <4>
LIBKI_MAX_WORKERS=4
LIBKI_SESSION_TIMEOUT=3600 // <5>
DB_NAME=libki
DB_USER=libki
DB_PASS=<DB_PASSWORD> // <6>
DB_ROOT_PASS=<DB_ROOT_PASSWORD>
----
<1> On every start the container creates a superadministrator with this name, or resets its password to this value if it already exists. If either value is empty, no administrator is created or changed, and you will have no way to log in.
<2> Instance name. Leave it empty for a single-library server. If set, the instance is created on first start; a named instance is a separate, multi-tenant space with its own users and settings.
<3> Find your timezone in the documentation https://metacpan.org/pod/DateTime::TimeZone::Catalog[here]. Defaults to `America/New_York`.
<4> The port published on the Docker host. The server listens on 3000 inside the container.
<5> Lifetime of a login session, in seconds.
<6> Required. The compose file hands `DB_*` to both MariaDB and Libki. MariaDB only applies them the first time the `db_data` volume is created; after that, changing them in `.env` does not change the database.

Then run `docker compose up -d` from the `docker` directory.

IMPORTANT: The container's port is published on the loopback address only (`127.0.0.1:<LIBKI_PORT>`), and the database port is not published at all. Libki is not reachable from other machines until you put a reverse proxy in front of it. The <<_setup_wizard,setup wizard>> can install and configure nginx for you; see <<_using_libki_server_with_tlsssl,Using Libki Server with TLS/SSL>> to do it by hand. For a quick local check, the administration interface is at `http://127.0.0.1:<LIBKI_PORT>/administration`. For a database shell, run `docker compose exec db mariadb -u root -p`.

The container itself reads the following environment variables, which compose fills in from the file above: `LIBKI_DB_DSN`, `LIBKI_DB_USER`, `LIBKI_DB_PASSWORD`, `LIBKI_INSTANCE`, `LIBKI_TZ`, `LIBKI_ADMIN_USERNAME`, `LIBKI_ADMIN_PASSWORD`, `LIBKI_SESSION_TIMEOUT`, `LIBKI_SERVER_PORT` and `LIBKI_MAX_WORKERS`. If you run the image without Docker Compose, set these yourself. (`LIBKI_DB_HOST`, `LIBKI_DB_PORT` and `LIBKI_DB_DATABASE` are only used by the `ldb` shell alias inside the container, not by the server.)

==== Cronjobs

The Libki cronjobs are not set to run inside the Docker container. Instead, it the cronjobs should be set up on the host machine.

Add the following to a file in `/etc/cron.d/` (this format has a user column):

```
* * * * * root docker exec <container-name> /app/script/cronjobs/libki.pl
0 0 * * * root docker exec <container-name> /app/script/cronjobs/libki_nightly.pl
```

If you use root's crontab (`sudo crontab -e`) instead, leave out the `root` column:

```
* * * * * docker exec <container-name> /app/script/cronjobs/libki.pl
0 0 * * * docker exec <container-name> /app/script/cronjobs/libki_nightly.pl
```

On a native install, `install.sh` sets these up for you (the `libki` user's crontab runs both scripts, and root's crontab restarts the service if it has stopped).

=== Using Libki Server with TLS/SSL

Libki Server does not have native SSL support. To use SSL with Libki, you should use a reverse proxy that supports SSL termination such as Apache, nginx, Traefik, etc. By default Libki uses Apache as its' proxy.

Once you have SSL set up, the proxy needs to send a custom HTTP header `X-Request-Base` with the value of your server URL using SSL. For example, if your FQDN is `libki.mylib.org`, set `X-Request-Base` to `https://libki.mylib.org`. With Apache this is `RequestHeader set X-Request-Base "https://libki.mylib.org"`; a commented example is included in `reverse_proxy.config`. With nginx it is `proxy_set_header X-Request-Base "https://libki.mylib.org";`.

NOTE: Do not set the `libki-instance` header unless you run a multi-tenant server. The header overrides the instance, so naming an instance that has not been created (see `script/administration/create_instance.pl`) makes logins fail.

=== Setup wizard

`script/utilities/setup-wizard.sh` (installed as `libki-setup` by `install.sh`) asks a few questions, using `whiptail` dialogs when it is available and plain prompts otherwise (`--plain` forces prompts).

* `--docker` writes `docker/.env` (mode 600) with your administrator account, timezone and port, and freshly generated database passwords. It can then set up nginx (below) and run `docker compose up -d`. An existing `.env` is backed up first.
* `--native` is for a server that already has its Perl dependencies and a database. It writes the database settings into `libki_local.conf`, runs `installer/update_db.pl` and creates the administrator account.

Without an option the wizard asks which one you want. `--no-start` skips the offer to start the containers, and `--no-nginx` skips the nginx question.

==== nginx front end (Docker)

The Docker container listens on `127.0.0.1` only, so the wizard offers to install and configure nginx as the public front end. This needs root on a Debian or Ubuntu host. It asks for the public host name (its DNS record must already point at this server) and one of:

* *An existing certificate and key.* Give the paths of the PEM files. The wizard checks that the key matches the certificate, warns if the certificate has expired or does not list the host name, and refuses to continue if they do not match. See <<_using_an_existing_certificate,Using an existing certificate>>.
* *Let's Encrypt.* It installs `certbot` and `python3-certbot-nginx` and requests a certificate, with HTTP redirected to HTTPS. Ports 80 and 443 must be reachable from the internet. It asks for an email address for expiry notices. If certbot fails, the site stays up on plain HTTP and the wizard prints the command to retry.
* *Plain HTTP.* No TLS. Only for testing or a trusted network.

The site is written to `/etc/nginx/sites-available/libki` (an existing file is backed up first) and enabled in `sites-enabled`. The wizard runs `nginx -t` before loading it, and removes the site again if nginx rejects it. The configuration sends the `X-Request-Base` header Libki needs, and allows uploads of up to 100 MB so print jobs can be sent through the server. IPv6 listeners are added only if the host has IPv6.

If you are not root, or the host is not Debian or Ubuntu, nothing is installed. The wizard writes the configuration to `docker/nginx-libki.conf` for you to place in nginx yourself.

Open ports 80 and 443 in your firewall. Do not open the Libki port.

==== Using an existing certificate

Choose "existing" in the wizard, or point `ssl_certificate` and `ssl_certificate_key` at your files if you configure nginx yourself. Check these first:

* The certificate file must contain the full chain: your certificate followed by the intermediate certificates. A leaf-only file works in some browsers and fails in others, and often in Libki clients.
* The private key must be PEM and must not have a passphrase, because nginx cannot ask for one when it starts. To remove a passphrase: `openssl pkey -in encrypted.key -out libki.key`.
* The certificate must list your host name (or a matching wildcard) as a subject alternative name.
* Both files must be readable by root. nginx reads them at start-up, before it drops privileges. Keep the key at mode 600.
* A `.pfx`/`.p12` bundle must be converted first: `openssl pkcs12 -in bundle.pfx -nocerts -nodes -out libki.key` and `openssl pkcs12 -in bundle.pfx -nokeys -out libki-chain.pem`.
* The wizard does not renew anything, and it points nginx at your files where they are. When you renew, replace the files in place and run `nginx -s reload`; nginx keeps using the old certificate until it is reloaded.
